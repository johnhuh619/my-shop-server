## 항목별 이력서 요약

## 1) Order 락 경합 구조 재설계 [분석]
- **문제**: `orders FOR NO KEY UPDATE`가 DB 시간 점유 `8.83%`, `max 2301.78ms`로 치솟음.
- **사고 깊이 포인트**: 단순 쿼리 튜닝이 아니라, Order/Inventory 이중 비관락·스케줄러·Async 이벤트·커넥션풀/스레드풀까지 시스템 레벨로 원인 분해.
- **해결**: 멱등성 로그(`inventory_operation_log`) 도입 + 긴 트랜잭션을 짧은 단계 트랜잭션으로 분해.
- **결과**: 핵심 락 쿼리 `mean 193.37ms → 1.86ms`, `max 2301.78ms → 1.86ms`(소표본 기준, 재검증 기준 명시).
- **이력서 한 줄**: 락 경합 병목을 멱등성 기반 트랜잭션 분리로 재설계해 `2.3s급` 락 지연을 `~1.86ms` 수준으로 완화.

## 2) JPA L1 캐시 트러블슈팅 [디버깅]
- **문제**: `SELECT ... FOR UPDATE`를 써도 같은 영속성 컨텍스트에서 stale 엔티티가 반환되는 케이스 발생.
- **사고 깊이 포인트**: JPA 동일성 보장과 락의 상호작용을 타임라인으로 분해해 재현·설명. 대부분의 개발자가 “`FOR UPDATE`면 최신 데이터를 읽는다”고 가정하는 지점에서, 프레임워크 내부 메커니즘(L1 캐시 동일성 보장)과의 비자명한 충돌을 정확히 짚어냄.
- **해결**: 스케줄러 외부 트랜잭션 제거, ID 목록 추출 후 개별 트랜잭션 처리, 필요한 구간 `REQUIRES_NEW`/`clear()` 적용.
- **결과**: PAID 주문이 EXPIRED로 잘못 전이되는 정합성 버그 제거.
- **이력서 한 줄**: L1 캐시와 비관락 상호작용 버그를 트랜잭션 경계 재설계로 해결해 상태 전이 정합성 이슈를 제거.

## 3) k6 경합 회귀 복구 [검증]
- **문제**: 결제 confirm 경합에서 성공률 하락(`91/100`)과 tail latency(`p95 ~10.1s`) 발생.
- **사고 깊이 포인트**: 락 문제를 “락 자체”가 아닌 상태 관측(stale) + 대기 경로 설계 문제로 재정의.
- **해결**: `PROCESSING` fast-path, 전이 구간만 락, 폴링 루프 `entityManager.clear()` 적용.
- **결과**: `checks 100%`, `http_req_failed 0%`, `p95 1310.97ms / 998.75ms` 복구. 데드락 시나리오도 `49.87% → 0%`.
- **이력서 한 줄**: k6 기반 경합 회귀를 구조적으로 복구해 결제 tail latency를 `10.1s → <1.4s`로 단축.

## 4) 결제-배송 비동기 설계 결정 [판단]
- **문제**: 결제 완료 후 배송 자동 생성을 동기/비동기 중 어떤 방식으로 둘지 결정 필요.
- **사고 깊이 포인트**: “외부 확정(PG 승인) + 내부 실패 가능 작업”을 한 트랜잭션에 묶는 위험을 장애 시나리오(A/B/C)로 모델링. 아직 발생하지 않은 장애를 사전에 구조적으로 차단하는 설계 판단.
- **해결**: `PaymentCompletedEvent` 기반 비동기 체인 + `RetryTask` 보상 + 멱등 배송 생성.
- **결과**: 결제 응답 지연 분리, 배송 실패가 결제 롤백으로 전파되지 않는 구조 확보.
- **이력서 한 줄**: 결제/배송 결합도를 낮춘 비동기 보상 설계를 통해 장애 전파를 차단하고 최종적 일관성을 확보.

## 5) Payment 테스트/멱등성 동시성 개선
- **문제**: 동시 결제 시 `save`-`commit` 타이밍 차이로 UNIQUE 경합 실패 다수 발생.
- **사고 깊이 포인트**: 격리수준/flush 시점/예외 재조회 패턴까지 고려해 실무형 멱등성 모델 정립.
- **해결**: `flush()` 조기 검증 + `DataIntegrityViolationException` 재조회 처리 + 테스트 현실화.
- **결과**: 결제 관련 테스트 `총 40개 통과`, 동시성 시나리오에서 DB 멱등성(1건 생성) 유지.
- **이력서 한 줄**: UNIQUE 제약 기반 멱등성 처리와 예외 재조회 패턴으로 고동시성 결제 정합성을 안정화.

## 6) 주문 목록 N+1 최적화
- **문제**: 목록 조회가 `2N+1` 쿼리로 증가.
- **사고 깊이 포인트**: 단순 fetch join이 아닌, 도메인 경계 고려해 Facade 집계 + IN 배치 조합으로 설계.
- **해결**: `Order+OrderItems`는 fetch join, `Refund/Delivery`는 배치 IN 조회로 분리.
- **결과**: 쿼리 수 `2N+1 → 3(상수)`, 배송 상태 응답 확장.
- **이력서 한 줄**: 주문 목록 조회를 Facade+배치 쿼리로 재구성해 N+1을 상수 쿼리로 최적화.

## 7) 검색 pg_trgm 도입
- **문제**: `%keyword%` 부분검색 유지 조건에서 성능 저하 리스크.
- **사고 깊이 포인트**: Postgres 전용 최적화와 H2 호환성의 충돌을 운영/개발 분리 관점으로 해결.
- **해결**: `lower(name) LIKE` 명시 쿼리 + Postgres 조건부 인덱스 초기화 전략.
- **결과**: UX 변경 없이 운영 최적화 경로 확보, 테스트 회귀 없음.
- **이력서 한 줄**: 부분검색 UX를 유지하면서 pg_trgm 기반 인덱스 전략으로 PostgreSQL 검색 성능 개선 기반을 구축.

## 8) 장바구니 설계 의사결정
- **문제**: 서버 사이드 Cart 도메인 신설 여부 판단.
- **사고 깊이 포인트**: 현재 API 역량(복수 아이템 주문), 복잡도 비용, 제품 단계 적합성을 함께 평가.
- **해결**: 프론트 로컬 장바구니 + 기존 주문 API 재사용.
- **결과**: 불필요한 서버 복잡도 증가 없이 요구사항 충족.
- **이력서 한 줄**: 단계에 맞는 아키텍처 절제로 서버 Cart 도입을 보류하고 기존 주문 API 활용으로 개발 효율을 확보.
